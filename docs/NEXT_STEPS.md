# 下一版计划：自选站点与附近站点比较

日期：2026-10-23。本文是后续计划，尚未实现，不计入简历中的已完成成果。

## 已确认的范围

用户选择一个起点中心站和一个终点中心站；程序自动发现两端周边站点，
展示可比较的公交走法。继续作为本地研究工具，不部署公共导航服务。
本轮不新增家庭地址、定位权限、乘客记录、地图服务或自动 ETA 采集。

“附近有两个站”不是异常：两个站都是候选，方向和后续线路可能完全不同。
不能只保留最近站，也不能把不同起点站的车辆视作在同一站“先来先坐”。

## 1. 先解耦固定案例入口

- 将界面的案例查询改造成网络、起点站、终点站、出发时刻和参数驱动的接口。
- 先在已加载局部路网内按站名/站号查询；保留现有两个案例作为快捷选项和回归测试。
- 候选搜索、缓存和途中决策都绑定网络哈希及查询参数，避免复用另一组端点的结果。
- 分开返回：未知站号、超出路网覆盖、声明网络内不可达、预算截断、运营状态未知。

验收：多个未写死答案的站点对可查询；起终点相同、方向错误和无路情况输出清楚。

## 2. 自动发现附近候选站

- 使用本地 BusStops 的坐标，按中心站计算地理距离，无需新增 API。
- 初始建议半径 400 米，可配置；中心站始终保留，默认最多自动选入每端 3 个站。
  这些只是可调整的实验参数，不代表最佳半径或完整覆盖；显示被限制的候选数。
- 显示站号、站名、直线距离、服务方向、路由覆盖状态，允许用户取消或替换候选。
- 全量站点目录与可路由网络不是一回事：能发现的站可能尚未接入路径搜索。
  不支持的站明确显示，不能静默替换成较远站或说“没有公交”。
- 对向站保持不同 ID，不自动连为跨站换乘；暂不新增途中跨站步行。

验收：同名对向站、半径边界、无近邻、中心站保留、候选截断及坐标校验均有测试。

## 3. 多起点、多终点公交方案比较

- 用户确认候选集合后，先用有预算的站点对查询比较，默认至多 3 x 3 组。
  共享目标索引可后续优化，不先引入复杂全网求解器。
- 每个方案显示实际上车站、下车站、途经服务、换乘站、乘车与站外等待拆分。
- 去重不能丢掉不同端点、方向或换乘站变体；近邻站较远但线路更好时仍有机会保留。
- 第一版默认指标是“在所选上车站就绪之后的公交段时间”，不是中心站到中心站总时间。
  因此不能把较远站的公交段更短直接宣布为整段出行更快。
- 可另行提供用户手工输入的起终端接驳分钟数；未提供时标为未知，不默认为零。
  输入接驳时间后，先平移上车站就绪时刻，再检查运营窗口或预测可接续性，
  不能仅在最终结果上加几分钟。终端接驳另行计入参考总时间。
- 直线距离只用于发现候选，不自动换算成已验证步行时间。

验收：加入附近站能找到可解释的替代方案；同步发车或绕行时也允许无收益；
同车继续不重复等待，不生成依赖未经确认跨街路径的“可执行”保证。

## 4. 扩展路网，而不是只扩展输入框

现有线路模型拒绝同一服务内重复站点，搜索又包含候选枚举；不能直接把全岛
CSV 填进当前模型就声称支持任意站点。下一步应先完成通用有向站序导入：

- 区分服务、方向、站序和停站事件；重复停站不能随意去重。
- 保留同车身份，不能通过拆段解决环线后再重复增加上车等待。
- 对未支持的模式显式报告覆盖缺口；在正确处理环线前不宣称全网可达性。
- 选择原案例之外的多组站点对，检查连通性、搜索预算、耗时和内存，再逐步扩区。
- 继续使用历史运营窗口和带标签的时间假设，未知 ETA 不删除拓扑可行候选。

阶段 1 至 3 可先在局部网络交付原型；面向全岛任意站点的版本必须经过本阶段验收。

## 优先级与非目标

最近一次实现应先完成阶段 1，再接阶段 2 和 3；不同时开发地址输入、真实步行网、
票价计算、机器学习或赶车概率。需要真实 ETA 时另开有明确请求预算的验证阶段。

成功标准：用户能自主选择站点，看到附近有哪些替代上车/下车点、为何值得比较，
并清楚哪些部分只是模型估计、哪些连接尚未验证。不要求超过 Google Maps。
